# Codebase Audit — November 2026

Scope: whole repository at `55fd0a5` — WebUSB JS stack, the two HTML pages, `resizeDNG.mjs`, the Android app (USB/service + UI/data/build), CI, and docs.

Method: five parallel reviewers (two on the protocol/concurrency-heavy code, three on UI, tooling and docs), followed by a manual re-check of the headline findings against the source. Items marked **✔** were re-read and confirmed in the consolidation pass; the rest were verified by the reviewer from the code but not independently re-checked. Line numbers are as of `55fd0a5`. Nothing was run on real hardware.

**Remediation status:**
- *Fixed:* top-10 items 1, 2, 3, 5, 6, 7 and 9, plus most of §1 and §3. This covers:
  - the crash and one-line fixes;
  - `resizeDNG.mjs` and the `multi-camera.html` XSS;
  - the transport rework on both platforms: one reader per camera, serialized RPC matched by id, notification routing, per-command timeouts, bounded and cancellable reads, alt-setting selection on Android, and corrected JPEG reassembly.
- *Remaining from §1/§3:* camera-side live-view stop (no known command), `SyncCaptureEngine` timing, the racy 4-camera limit on Android, the stable fallback id, and the vendor/product filter.
- *Open:* items 4, 8 and 10, and §4–§6.
- *Not yet tested:* none of the fixes has been run against real hardware.

**Top 10 to fix first**

1. ✔ **Android 14 crash on permission request.** An implicit intent is wrapped in a `FLAG_MUTABLE` PendingIntent (`UsbDeviceManager.kt:157-168`).
2. ✔ **Commands are not serialized and replies are not matched by id, on both platforms.** Live view and RPC share one bulk-IN endpoint, so replies and JPEG packets get swapped (`dxo1usb.js:177-282`, `CameraDevice.js:273-405`, `DxoOneUsbProtocol.kt`).
3. ✔ **Android read loops never end on a 0-byte read.** An unplugged camera pegs an IO thread at 100% CPU, and the loop can't be cancelled (`DxoOneUsbProtocol.kt:141-152, 193-201`).
4. ✔ **The Android project can't be built as committed.** There is no `gradlew`, `gradlew.bat` or `gradle-wrapper.jar`.
5. ✔ **Shell injection in `resizeDNG.mjs:33`.** Filenames are passed unquoted into `execSync`. The script also creates `resized/` in the wrong directory (`:27`).
6. ✔ **XSS in `multi-camera.html`.** A USB serial number or nickname can break out of the `onclick="..."` and `title="..."` attributes, because `escapeHtml` doesn't escape `"`.
7. ✔ **`setSettings.*` throws whenever the camera confirms a setting.** `result` is undefined at `dxo1usb.js:217`.
8. ✔ **Android "Apply settings" reports success when every command failed, and never sends "Auto"** (`SettingsViewModel.kt:138-191`).
9. ✔ **Wrong protocol values in JS.** `tnrOff` sends `"on"` (`dxo1usb.js:301`), night mode sends `" night"` with a leading space (`:421`), and `getDigitalZoom` is invoked at open instead of being a function (`:487`).
10. **CI can't fail.** Every meaningful job has `continue-on-error: true` or `|| echo`, there are no tests, and the Android app is never built.

## 1. JavaScript USB stack

### Critical
- **✔ Unserialized RPC with no reply correlation; live view shares the IN endpoint.** `dxo1usb.js:177-201, 228-282`; `CameraDevice.js:273-302, 339-405`. `transferOutRPC` sends a request and then reads whatever arrives next. `res.id` is never compared with `seq`, and nothing stops two commands overlapping. `stopLiveView` only sets a flag (`// TODO: turn this off from the camera side too`), so the camera keeps streaming.
  - *Scenario:* start live view on camera A, then press "Capture All". A's `takePhoto` reads JPEG packets as an RPC header, `metadata[8] + (metadata[9] << 8)` produces a garbage size, and the result is a RangeError, a `null` result, or a hang.
  - *Fix:* add a per-device promise queue around each send/receive pair, match replies by id, and route unmatched messages to an event handler. Make stop switch the camera out of view mode and wait for the loop to exit.

### High
- **✔ `setSettings.*` throws a ReferenceError.** `dxo1usb.js:217` reads `result.id`, and `result` is undefined. It should be `response?.id === commandSeq && response?.result?.type === params.type`. Line 215 also throws if `immediateResponse` is null.
- **✔ `getDigitalZoom` is not a function.** `dxo1usb.js:487`: the RPC fires, unawaited, during `open()`, where it races the caller's first command; calling `command.getDigitalZoom()` afterwards throws. Wrap it as `() => transferOutRPC(...)`.
- **Capture All reports failed cameras as successful and has no timeout.** `CameraManager.js:318-370`, `CameraDevice.js:245, 262, 309-311`. `transferInRPC` returns `null` for bad frames, and JSON-RPC `error` replies resolve normally, so both become `status: 'success'`. One camera that stops responding hangs `captureAll()` forever. The initialization drain loop (`CameraDevice.js:108-115`) can also hang. This breaks INV-MULTI-003 and INV-CONS-003.

### Medium
- **✔ Split live-view frames are corrupted when reassembled.** `dxo1usb.js:255-258`, `CameraDevice.js:369-372`. `set(accumulated)` followed by `set(frame, lastLength - foundHeaderIndex)` overwrites the tail of the old data, or throws a RangeError. Use `mergeU8A(accumulated.subarray(foundHeaderIndex), frame)`.
- **✔ The 32-byte header is never stripped.** `dxo1usb.js:93`, `CameraDevice.js:184`: `indexOfMulti` searches the freshly zeroed `jpgResponse` buffer instead of `metadata`. On top of that, `dxo1usb.js:245/268` requires `> 0`, which skips a header at index 0. A header at index 0 means no frame is ever emitted, and the buffer grows without bound.
- **Object URL leak in single-camera live view.** `dxo1usb.js:248, 271` create a URL per frame, and `usb.html` never revokes them. `multi-camera.html:231-236` leaks the last URL on each stop.
- **Unplugging during live view leaves state stuck.** `CameraManager.js:429-441` doesn't stop live view or clear `isLiveViewActive`. The pending `transferIn` rejects unhandled, and `startLiveView()` is never awaited or caught.
- **A quick stop then start runs two live-view loops** (`dxo1usb.js:226-233, 279-282`), because both share the `shouldStopLiveView` flag.
- **Fragile RPC framing** (`dxo1usb.js:131-157`, `CameraDevice.js:223-249`). The `A3 BA D1 10` header isn't validated, an oversized packet throws a RangeError on `set()`, and leftover bytes stay in the pipe and corrupt the next command.
- **Failed initialization leaves the device open** (`CameraDevice.js:125-130`), contrary to STATE_MACHINES.md, and `_refreshStatus` swallows errors.

### Low
- `CameraDevice.js` is a copy of the `dxo1usb.js` protocol code rather than a user of it, and the two copies have already drifted (`>= 0` vs `> 0`, revoke callback vs none, `null` vs `undefined`).
- The fallback ID `${vendorId}-${productId}-${Date.now()}` (`CameraDevice.js:50`) isn't stable across reconnects (INV-MULTI-001).
- `new Uint8Array(res.data.buffer)` ignores `byteOffset` and `res.status`. Lengths are 16-bit, so a payload of 64 KB or more wraps silently (INV-DATA-001).
- The device filter matches `vendorId` only (INV-SEC-001), and there is no allowlist of RPC methods (INV-SEC-003).
- `u8a.js` is correct. The only issue is dead code: `payloadStrHuman`'s regex `/\[\]/g` matches the literal `[]`.

## 2. Web pages, `resizeDNG.mjs`, CI

### High
- **✔ Shell injection: `resizeDNG.mjs:33`.** The `sips` command line is built with string interpolation and run through `/bin/sh`. Reproduced: a file named `a;touch PWNED;.DNG` executed `touch`. Directory paths with spaces also break. *Fix:* `execFileSync('sips', [...args])`.
- **✔ `resized/` is created in the wrong directory.** `resizeDNG.mjs:27` does `mkdirSync('resized')` in the current working directory, but sips writes to `${dngPath}/resized/`. The script fails unless `dngPath` is `.`. *Fix:* `mkdirSync(path.join(dngPath, RESIZED_DIR), {recursive: true})`.
- **INV-DATA-002 (colorspace preservation) is claimed but not implemented.** The script runs a bare `sips -s format jpeg` with no profile handling and no test. It is also macOS-only, which the package and docs don't mention.
- **✔ XSS in `multi-camera.html` attributes.** Lines 50-51, 62 and 124-129 are affected.
  - `camera.id` comes from the device's `serialNumber`. `escapeJsString` turns `"` into `\"`, but the HTML parser still ends the `onclick` attribute at that `"`.
  - `escapeHtml` (`textContent` → `innerHTML`) doesn't escape quotes, so `data-camera-id="…"`, `title="${lastError}"` and `id="btnLiveView-…"` can also be broken out of.
  - The comment "Bug fix: escape camera ID to prevent XSS" is misleading.
  - *Fix:* replace inline handlers with `addEventListener` and `data-*` attributes, and build the nodes with `textContent`.

### Medium
- **`usb.html` has no error handling.** If `open()`, `getAllSettings()`, `takePhoto()` or `liveView.start()` throws, the UI is left half-updated. `log()` uses `innerHTML` with camera-supplied JSON.
- **`multi-camera.html:226-240`.** `startLiveView` isn't awaited or caught, so a failure leaves "Stop Live View" showing permanently.
- **CI proves nothing.**
  - `npm test` runs `node --check` on 3 files and skips `CameraDevice.js`, `CameraManager.js` and the HTML modules.
  - The lint, test and build jobs all have `continue-on-error: true`, and the lint script is just `echo`.
  - The syntax step's `&& echo ✅ || echo ❌` swallows the exit code.
  - The invariant and doc-link "checks" are greps that only print warnings.
  - The summary job always prints success.
  - The Android app is never built.
- **`.gitignore` doesn't cover the Android project.** `local.properties`, `.gradle/`, `build/`, `*.apk`, `*.aab`, `*.jks`/`*.keystore`, `.idea/` and `.env` can all be committed.

### Low
- The workflow has no top-level `permissions:` block (add `contents: read`). Actions are pinned by tag rather than SHA. Node 18 is end-of-life, and there is no `concurrency` group.
- Neither page has a CSP. `usb.html` has no doctype or charset (quirks mode) and no `alt` on its image.
- In `resizeDNG.mjs`, `.dng` (lowercase) files are skipped, `x.DNG.bak` is matched, the catch dereferences `e.stderr` without checking it, one failure aborts the whole batch, and the output size is hard-coded for 5540×3688 landscape.

## 3. Android — USB and service layer

The frame layout (8-byte header, little-endian length at bytes 8-9, 22-byte trailer, JSON plus NUL) matches `dxo1usb.js`. The defects are in transfer handling, lifecycle and concurrency.

### Critical
- **✔ Android 14 crash on the permission request.** `UsbDeviceManager.kt:157-168` passes `Intent(ACTION_USB_PERMISSION)`, an implicit intent, with `FLAG_MUTABLE`. Apps targeting SDK 34 get an `IllegalArgumentException`. *Fix:* `.setPackage(context.packageName)`, and keep it mutable because the USB service fills in the extras.
- **✔ No per-camera lock on USB traffic.** `grep Mutex` finds nothing in `usb/` or `service/`. Live view starts on connect (`MultiCameraViewModel.performConnect`) and calls `receiveJpegFrame()` in a tight loop, while `takePhoto()`, `setSetting()` and `refreshStatus()` read the same IN endpoint. `sequenceId++` is unsynchronized. `CameraManagerService.applySettingToAll` fires commands without waiting and always returns `true`.

### High
- **✔ Read loops spin forever on timeout or detach.** `transferIn` returns `ByteArray(0)` on any error (`DxoOneUsbProtocol.kt:241`). The RPC loop advances `offset` by 0, and the JPEG loop is `while (true)` until it sees `FFD9`. Neither loop suspends or checks `isActive`, so cancelling the job doesn't stop it. *Fix:* treat a negative return as fatal, cap consecutive empty reads, call `ensureActive()`, and join the live-view job before calling `close()`.
- **The setting-applied notification is counted as success, and response ids are never checked.** `JsonRpcMessage.kt:54` treats `error == null` as success. The JS reference (`dxo1usb.js:214-217`) reads a second response after `dxo_setting_applied`, but Kotlin doesn't, so every later command reads the previous command's reply.
- **✔ Alternate setting 1 is never selected.** `CameraConnection.kt:89` says "setInterface not directly available", but `UsbDeviceConnection.setInterface()` has existed since API 21. `DxoOneConstants.ALTERNATE_SETTING` is unused, and `getInterface(1)` is a descriptor index, not alt-setting 1. The JS reference calls `selectAlternateInterface(1, 1)`.
- **Likely crash on detach.** `UsbDeviceManager.kt:247` reads `device.serialNumber`, which is never used. On Android 10+ that read needs permission, which may already be revoked when `DETACHED` is broadcast. Not tested on a device; delete the line.
- **"Synchronized" capture isn't synchronized.** `SyncCaptureEngine.kt:54-73`: `timestamp` is taken before the ACK round-trip and the Gson serialization, so `syncVarianceMs` measures how far apart the coroutines started (under 1 ms), not when the shutters fired.

### Medium
- **One 5 s timeout for every read.** `CAPTURE_TIMEOUT_MS` (30 s) and `COMMAND_TIMEOUT_MS` are unused. A long exposure times out, and the late reply then shifts every later response by one.
- **`transferOut` return values are ignored.**
- **The 4-camera limit is racy.** The size check runs before a suspending `initialize()`. Connecting the same device twice opens it twice with `force=true` under the same id, and the first connection leaks along with its live-view loop.
- **`CameraManagerService` is dead code.** Nothing starts or binds it.
  - If it were started, its `initialize()`/`cleanup()` calls would collide with the ViewModel's.
  - On Android 14, a `START_STICKY` restart without USB permission would throw from `startForeground` with type `connectedDevice`.

### Low
- The opened connection leaks when `getInterface(1)` throws.
- `startLiveView` creates a new unscoped `CoroutineScope`, and the job it replaces is never cancelled.
- `receiveJpegFrame` boxes every byte in a `List<Byte>` and rescans the whole buffer per packet (quadratic), and it drops any bytes after `FFD9`.

## 4. Android — UI, data, DI, build

### Critical
- **✔ The project can't be built as committed.** `git ls-files android-app` shows only `gradle-wrapper.properties`: there is no `gradlew`, `gradlew.bat` or `gradle-wrapper.jar`, yet `android-app/README.md:42,51` says to run `./gradlew`. *Fix:* `gradle wrapper --gradle-version 8.4` and commit the output.

### High
- **`Icons.AutoMirrored.Filled.ArrowBack` probably doesn't compile.** It's used at `MainActivity.kt:14` and `SettingsScreen.kt:54`, but the Compose BOM `2023.10.01` resolves to Material 1.5.x, and AutoMirrored arrived in 1.6. *Unconfirmed*: no build was possible without the wrapper.
- **✔ Apply Settings always reports success.** `SettingsViewModel.kt:138-190` discards the Boolean returned by `setSetting()`, which never throws (`CameraConnection.kt:216-229`), so `successCount++` always runs.
- **✔ "Auto" is never sent.** `SettingsViewModel.kt:145, 158` skip ISO and exposure time when they're AUTO, so changing back from a manual value leaves the camera on that value. The JS reference sends `"auto"` explicitly. Aperture and shutter values are also dropped outside their shooting modes.
- **Saved settings are never applied when a camera connects** (`MultiCameraViewModel.performConnect`), so a re-plugged camera silently diverges from the others.

### Medium
- **Each Apply starts another live-view loop.** `SettingsViewModel.kt:185` → `CameraConnection.startLiveView`, which has no guard.
- **`selectedCameraIds` is a plain `mutableSetOf` changed from both IO and Main** (`MultiCameraViewModel.kt:50, 318`), so a `ConcurrentModificationException` is possible.
- **Connection and battery state only reach the UI when a frame arrives or the camera map changes** (`updateCameraStates`), so a camera that drops to ERROR still shows CONNECTED (INV-DATA-003).
- **`MainActivity` has no `launchMode`.** With the `USB_DEVICE_ATTACHED` filter, each attach can start a new instance with its own ViewModel. Each calls `initialize()`, which isn't idempotent, and each one's `onCleared` disconnects every camera.
- **The service is never started**, and `POST_NOTIFICATIONS` is never requested at runtime.
- **The capture snackbar replays on navigation**, because `lastCaptureResult` is never consumed (`MainScreen.kt:81-90`).

### Low
- `collectAsState()` is used instead of `collectAsStateWithLifecycle()`.
- Reset leaves `applyToAllCameras` stale in the UI, and settings loading races user edits.
- `enumValueOf` in `SettingsPreferences.kt:21-42` will crash the Flow if an enum constant is ever renamed.
- `UsbDeviceManager` is bound twice, by both `@Inject` and `@Provides`.
- `minSdk 21` but icons exist only in `mipmap-anydpi-v26`.
- `READ_EXTERNAL_STORAGE` and the Room dependency are unused, the Gallery route is unreachable, and `Theme.kt:60` casts `view.context as Activity`.

Checked and fine: one DataStore instance and no blocking reads; the Hilt wiring; AGP 8.2, Gradle 8.4, Kotlin 1.9.20, Compose compiler 1.5.5 and Hilt 2.48 are compatible with each other; `LazyVerticalGrid` uses stable keys; setting key names match `dxo1usb.js`.

## 5. Invariants vs. enforcement

There is no test file anywhere in the repo. Every "unit test", "integration test", "runtime assertion", "type check" and "fuzzing" item listed under *Enforcement* in `docs/INVARIANTS.md` is unimplemented. In particular:

- **INV-DATA-001:** no type or length validation before sending, and lengths silently wrap at 64 KB.
- **INV-DATA-002:** no colorspace handling at all (see §2).
- **INV-DATA-003:** violated on Android (stale UI state) and in the JS live-view path.
- **INV-SEC-001 / INV-SEC-003:** filter by vendorId only, no RPC method allowlist.
- **INV-MULTI-001:** the fallback ID is time-based.
- **INV-MULTI-003:** null and error replies are counted as success, and the code comment claims `Promise.allSettled` while the code uses `Promise.all` plus `.catch`.
- **INV-MULTI-004:** the "~50 ms" sync figure is never measured on either platform.
- The `prompts/` files all say "11 invariants"; INVARIANTS.md lists 15, and none covers Android.

## 6. Documentation drift

**User-facing instructions that fail if followed**
- `docs/USER_GUIDE.md` (~L345-370, L545) documents `node resizeDNG.mjs input.dng output.jpg`. The script actually takes one directory argument, matches only uppercase `.DNG`, needs macOS `sips`, and depends on the current working directory.
- `android-app/README.md` says to run `./gradlew`, which isn't committed.
- `USER_GUIDE.md` says "No mobile support" but never mentions the Android app.
- `USER_GUIDE.md` lists settings (EV range, self-timer, video Mbps, manual-focus range, and others) that aren't all exposed by `setSettings`. Its code samples have no `import` lines.
- `ANDROID_MULTI_CAMERA_APP.md` Appendix C points to a command reference in USER_GUIDE.md that doesn't exist.

**Architecture and state-machine drift**
- `ARCHITECTURE.md` never mentions `android-app/` and still lists a native mobile app as future work. ROADMAP and DECISIONS are likewise stale.
- `ARCHITECTURE.md` draws `dxo1usb.js` below `CameraDevice`. In reality `dxo1usb.js` re-exports CameraDevice and CameraManager, and `CameraDevice` doesn't use it at all.
- `STATE_MACHINES.md`:
  - The Kotlin initial state is `INITIALIZING`, not `DISCONNECTED`.
  - CONNECTED→ERROR on a communication error isn't implemented.
  - There is no `cleanup()` on `CameraConnection`.
  - The JS `CameraDevice(device, usbBackend)` signature is wrong; the real one is `(usbDevice, nickname)`.
  - The READY, CAPTURING and CLOSED states are not real; the code only derives state from booleans.
- `ANDROID_MULTI_CAMERA_APP.md` is headed "IMPLEMENTED", but every roadmap checkbox is unchecked. The listed project structure includes files that don't exist (`UsbModule.kt`, `data/repository`, Room DAO/DB, `domain/usecase`, `LiveViewStream.kt`, `GalleryScreen.kt`, `CaptureViewModel.kt`), and Phase 4 (image download/gallery) is not implemented.
- `ROADMAP.md`:
  - "CI/CD Pipeline" is unchecked, but `ci.yml` exists.
  - Phase 3 lists live view and ISO/aperture/shutter control as future work, but both are already implemented.
  - Phase 2 excludes multi-camera support, while Phase 1 lists it as delivered.

**Minor**
- `ARCHITECTURE.md` still has `[TBD]` markers that the code already answers.
- Doc dates are inconsistent (2025 vs 2026).
- `prompts/usb-protocol-debug.md:268` uses made-up opcodes (`cmd: 0x15`) instead of the JSON-RPC `dxo_*` protocol.
- The Lightning-variant notes contradict each other in strength.

## Suggested remediation order

1. **Fix crashes and correctness.**
   - Android PendingIntent `setPackage`.
   - JS: `result` → `response`, the `getDigitalZoom` thunk, and the `tnrOff` / `" night"` values.
   - `resizeDNG.mjs`: switch to `execFileSync` and fix the mkdir path.
   - `multi-camera.html`: remove the inline handlers.
2. **Make the transport sound on both platforms.** Add a per-camera mutex/queue, match replies by id, handle notifications, use per-command timeouts, end Android reads on negative returns, and pause or stop live view on the camera side before sending commands.
3. **Make the build and CI real.** Commit the Gradle wrapper, remove `continue-on-error`, `node --check` all JS, add an Android `assembleDebug` + lint job, and add a small mocked-`navigator.usb` test suite for framing and reassembly.
4. **Fix the Android lifecycle.** Use `singleTop`, make `initialize()` idempotent, give the service clear ownership (or delete it), apply saved settings on connect, and expose state through `combine`d flows.
5. **Reconcile the docs with the code.** Prioritize USER_GUIDE.md's resize instructions, ARCHITECTURE.md's Android coverage, and INVARIANTS.md's enforcement claims.
